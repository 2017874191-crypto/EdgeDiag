# EdgeDiag 第一版目标、约束与取舍

## 1. 文档目的

本文定义 EdgeDiag 第一版的目标、范围、约束、非目标和技术取舍，作为后续设计、开发和验收的基线。

第一版的重点不是覆盖所有工业物联网能力，而是完成一条可靠、可测试、可解释的端到端闭环：

```text
设备数据产生 → MQTT 接入 → 异常检测 → Agent 诊断 → 结构化结果 → MQTT 返回
```

第一版必须能够在没有真实硬件的情况下运行，并为未来接入 STM32 硬件保留稳定的协议和模块边界。

## 2. 项目定位

EdgeDiag 是一个面向工业设备的边缘智能诊断原型系统，包含：

- 设备侧遥测数据产生与命令响应；
- Linux 侧 MQTT 数据接入与设备状态管理；
- 基于规则和统计特征的异常检测；
- 基于工具调用和知识检索的 Agent 诊断；
- 诊断结果、证据和设备命令的结构化管理；
- 故障注入、自动化测试和全链路追踪。

第一版面向三个目标岗位展示能力：

1. 嵌入式软件：实时任务、协议、可靠通信和故障恢复；
2. Agent 开发：工具调用、RAG、工作流和结构化输出；
3. Agent Infra：任务运行时、权限、重试、Trace 和评测。

## 3. 第一版目标

### 3.1 功能目标

第一版必须完成以下闭环：

1. 设备模拟器按照设备协议周期发布温度、振动和电流数据；
2. Linux 服务通过 MQTT 接收并校验遥测数据；
3. 系统能够处理重复消息、乱序消息和设备离线；
4. 系统能够识别温度、振动和联合异常；
5. 异常被建模为具有生命周期的 Incident；
6. Agent 可以查询设备状态、历史遥测和故障知识；
7. Agent 输出结构化诊断报告，而不是只有自然语言；
8. 诊断结果包含证据、候选原因、置信度和建议动作；
9. 低风险命令可以执行，高风险命令必须人工确认；
10. 设备模拟器能够接收命令并返回 ACK；
11. 端到端流程能够通过 Docker Compose 一键启动；
12. 每次诊断能够通过 trace_id 追踪完整执行过程。

### 3.2 技术目标

第一版需要证明以下工程能力：

- 协议版本化和 Schema 校验；
- MQTT QoS、重连、心跳和命令 ACK；
- 消息去重和命令幂等；
- 规则检测与 Agent 推理分层；
- Agent 工具白名单和权限控制；
- 模型失败时降级到规则诊断；
- 结构化输出校验和错误恢复；
- 故障注入与自动化回归测试；
- 设备、消息、Incident、Agent Task 的统一关联；
- 基础指标、日志和 Trace。

### 3.3 交付目标

第一版交付以下内容：

- 可运行的设备模拟器；
- 统一设备协议文档和 JSON Schema；
- Linux MQTT 接入服务；
- 规则和统计异常检测服务；
- 单 Agent 诊断工作流；
- 设备手册/故障码知识库；
- 诊断结果 API；
- MQTT 命令和 ACK 闭环；
- 故障注入脚本；
- 自动化测试和评测报告；
- Docker Compose 部署文件；
- 架构、故障处理和运行说明。

## 4. 第一版范围

### 4.1 设备范围

第一版只模拟一种设备：

```text
电机/风机振动监测设备
```

设备指标只包含：

- 温度；
- 振动 RMS；
- 电流；
- 设备在线状态；
- 固件版本；
- 采样周期；
- 消息序列号。

### 4.2 异常范围

第一版只支持三类异常：

1. 温度持续超过基线；
2. 振动 RMS 持续超过基线；
3. 温度和振动同时上升。

同时支持以下通信和数据故障：

- 设备离线；
- MQTT 断线；
- 重复消息；
- 乱序消息；
- 传感器数据无效；
- Agent 超时；
- 知识库无匹配结果。

### 4.3 Agent 范围

第一版只实现一个 Agent：

```text
DeviceDiagnosticAgent
```

第一版只允许 Agent 使用以下工具：

- `get_device_status`；
- `query_telemetry`；
- `calculate_signal_features`；
- `run_anomaly_detector`；
- `search_device_manual`；
- `get_fault_code_info`；
- `request_command_confirmation`。

Agent 的输出必须符合固定 Schema，至少包含：

- Incident ID；
- 设备 ID；
- 严重程度；
- 摘要；
- 证据；
- 候选原因；
- 置信度；
- 建议动作；
- 是否需要人工确认。

## 5. 系统边界

### 5.1 设备端边界

第一版设备端由模拟器实现，协议和行为按照未来 STM32 固件设计。

设备端负责：

- 生成或采集遥测数据；
- 维护 `device_id`、`boot_id` 和 `seq`；
- 发布遥测；
- 接收配置和控制命令；
- 返回命令 ACK；
- 模拟断线、重连和故障。

设备端不负责：

- 调用大模型；
- 检索知识库；
- 访问 Linux 数据库；
- 自主执行未经授权的高风险操作。

### 5.2 Linux 服务边界

Linux 服务负责：

- MQTT 消息接入；
- Schema 校验；
- 去重和乱序处理；
- 设备状态维护；
- 遥测存储；
- 异常检测；
- Incident 管理；
- Agent Task 调度；
- MQTT 命令发布；
- 诊断结果持久化。

### 5.3 Agent 边界

Agent 负责：

- 理解 Incident 上下文；
- 调用白名单工具；
- 获取历史和知识证据；
- 形成诊断假设；
- 生成结构化报告；
- 建议下一步动作。

Agent 不负责：

- 直接访问数据库或 MQTT Broker；
- 自行决定高风险动作；
- 替代规则检测；
- 直接修改设备保护阈值；
- 输出未经 Schema 校验的结果。

## 6. 技术取舍

### 6.1 先做模拟器，不等待硬件

取舍：第一版先使用 Python 设备模拟器，后续再接入 Zephyr/STM32。

原因：

- 当前没有硬件；
- 可以优先验证 Linux、协议、Agent 和可靠性；
- 可以批量注入异常和网络故障；
- 模拟器与真实固件共享协议，后端无需重写。

代价：

- 第一版不能证明真实 MCU 的内存、实时性和功耗；
- 需要后续增加真实板级测试。

补偿措施：

- 协议独立维护；
- 设备端行为采用状态机；
- 保留 Zephyr Native/STM32 固件目录；
- 对协议和任务逻辑做 Host 测试。

### 6.2 先用 Zephyr/Native，再接 STM32

取舍：不从零实现 RTOS、网络协议栈和 MQTT 客户端。

参考项目：

- Zephyr：RTOS、设备驱动、MQTT、TLS、测试和 Native 模拟；
- MCUboot：安全启动和固件升级；
- Mosquitto：MQTT Broker。

原因：

- 把精力集中在设备协议、可靠性和诊断能力；
- 避免重复实现成熟基础设施；
- 后续可以平滑迁移到 STM32 板卡。

代价：

- 对 Zephyr 构建系统、Kconfig 和 DeviceTree 有学习成本；
- 如果岗位强依赖 STM32 HAL，需要补充 CubeMX/HAL 版本。

补偿措施：

- 设备应用代码与底层驱动隔离；
- 保留 HAL/FreeRTOS 适配层设计；
- 后续增加 STM32CubeIDE 构建目标。

### 6.3 先用 Mosquitto，不自研 Broker

取舍：直接使用成熟 MQTT Broker。

原因：

- Broker 不是本项目的核心能力；
- 可直接测试 TLS、ACL、QoS 和 retained message；
- 可以将精力放到客户端可靠性和业务协议。

不做：

- 自研 MQTT Broker；
- 自研 MQTT 协议栈；
- 自研消息队列系统。

### 6.4 单 Agent，不做多 Agent

取舍：第一版只实现 `DeviceDiagnosticAgent`。

原因：

- 单 Agent 足以证明工具调用、RAG、结构化输出和可靠性；
- 多 Agent 会增加路由、上下文合并、冲突处理和评测复杂度；
- 当前故障场景不需要并行协作。

后续只有在以下条件满足时才拆分 Agent：

- 诊断领域出现明确的职责边界；
- 单 Agent 工具数量明显增加；
- 已经有可重复的评测集；
- 拆分能够降低延迟或提高准确率。

### 6.5 规则先于 LLM

取舍：异常识别由规则/统计模型完成，LLM 负责解释和编排。

原因：

- 异常检测需要可重复；
- LLM 不应承担硬实时或安全判断；
- 模型不可用时系统仍能告警；
- 便于评估误报率、漏报率和检测延迟。

第一版使用：

- 阈值检测；
- 滑动窗口；
- 均值和标准差；
- RMS、峰值和趋势；
- 可选 Isolation Forest。

暂不使用：

- 端到端深度学习诊断；
- 在线模型训练；
- 让 LLM 直接读取原始高频波形并自主判断。

### 6.6 结构化结果优先于自然语言

取舍：所有诊断先输出 JSON，再由前端或 Agent 生成自然语言展示。

原因：

- 便于设备和服务消费；
- 便于测试和回归；
- 便于审计；
- 防止模型输出不可解析内容。

所有输出必须经过 Pydantic 或 JSON Schema 校验。

### 6.7 只读工具优先，写操作受控

取舍：第一版大多数工具为只读工具，设备控制只保留低风险配置。

允许：

- 查询状态；
- 查询历史数据；
- 计算特征；
- 查询手册；
- 修改采样周期；
- 请求人工确认。

暂不允许：

- 自动停机；
- 自动修改保护阈值；
- 自动清除故障；
- 自动执行固件升级；
- 自动提高设备负载。

## 7. 非目标

第一版明确不做以下内容：

- 多种真实设备型号；
- 大规模设备集群；
- 完整工业 SCADA；
- 自研时序数据库；
- 自研 MQTT Broker；
- 自研 RTOS；
- 多 Agent 并行系统；
- 复杂的 Web 大屏；
- 自动化高风险控制；
- 完整 OTA 灰度发布平台；
- 复杂的在线模型训练；
- 生产级多租户和计费系统。

这些功能可以作为后续版本，但不能进入第一版核心验收范围。

## 8. 第一版验收标准

### 8.1 功能验收

- 模拟设备能够发布遥测；
- 服务能够校验并持久化数据；
- 重复消息不会重复创建事件；
- 设备离线能够产生事件；
- 温度/振动异常能够生成 Incident；
- Agent 能够调用至少三个诊断工具；
- 诊断结果包含证据和结构化字段；
- 命令能够通过 MQTT 返回设备；
- 设备能够返回 ACK；
- 模型失败时能够输出规则降级结果。

### 8.2 可靠性验收

- MQTT 断线后能够自动恢复；
- 重复命令不会重复执行；
- 服务重启后未完成任务不会丢失；
- Agent 超时后能够重试或降级；
- 非法模型输出不会进入设备控制链路；
- 每次诊断都能通过 `trace_id` 定位。

### 8.3 测试验收

- 协议 Schema 有自动化测试；
- 设备模拟器支持至少三种故障场景；
- 有重复、乱序和断线测试；
- 有 Agent 工具调用测试；
- 有结构化输出测试；
- 有至少一组诊断回归数据集；
- Docker Compose 可以启动完整演示环境。

## 9. 后续版本方向

第一版稳定后，再按以下顺序扩展：

### V1.1：真实 STM32

- STM32/Zephyr 板卡；
- I2C/SPI/ADC 传感器；
- DMA 采集；
- 看门狗；
- Flash 离线缓存；
- 真实网络延迟和丢包测试。

### V1.2：安全升级

- MCUboot；
- 固件签名；
- A/B 镜像；
- 失败回滚；
- 升级状态上报。

### V1.3：设备生命周期管理

- hawkBit 或等价 OTA 服务；
- 设备分组；
- 灰度发布；
- 升级策略；
- Agent 辅助升级建议。

### V2：Agent Runtime 增强

- 参考 Orbit 接入统一 Turn/Session；
- 异步诊断任务；
- 更细粒度的工具权限；
- 多模型 Provider；
- Agent 轨迹回放；
- 自动化基准评测。

## 10. 最终判断标准

第一版完成的标志不是“页面能显示数据”，而是以下闭环可以稳定运行：

```text
故障注入
  → 消息接入
  → 数据校验
  → 异常检测
  → Incident 创建
  → Agent 查询工具
  → 知识检索
  → 结构化诊断
  → 人工确认
  → MQTT 命令
  → 设备 ACK
  → Trace 和评测记录
```

第一版的核心取舍可以概括为：

> 少做设备类型，做深协议和可靠性；少做 Agent 数量，做深工具和边界；少做界面，做深测试、追踪和故障恢复。
