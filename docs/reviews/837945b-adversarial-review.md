## 结论

已有事务、请求回执、冻结遥测快照、工具边界等机制在针对性反例上有可观察作用。系统仍存在 3 项可复现问题，不能因为原 43 项回归通过就判定可靠性闭环成立。Agent/检索的真实质量收益尚无领域基准证明。

第一性需求是：采集事实可追溯、状态变更一致、重试不重复产生业务任务、故障后服务可继续提供能力、输出不越过证据与权限。组件数量和目录结构不是这些需求的证据。

## 已确认问题

### AUD-001 / P1：暂态数据库故障会终止 worker

位置：services/jobs.py:20（claim_job 在 try 外）；services/app.py:47 的 health 未检查 worker 活性。

复现：排入一个任务，首次领取注入 sqlite3.OperationalError，之后数据库正常。唯一测试 worker 退出，任务一直 queued。默认 2 个 worker 若相继遭遇该异常也会耗尽执行能力；当前健康接口仍静态返回 ok。

这是暂态依赖失败变成长期服务失效的问题。领取和结果持久化的故障边界应统一考虑，增加可取消的有限退避、明确失败告警/就绪状态；不要简单无限吞异常。测试应验证恢复后任务前进、取消不被吞掉以及持续故障不忙循环。

原始证明：audit/test_counterexamples.py::test_worker_survives_transient_claim_failure，展开 xfail 后 queued != completed。

### AUD-002 / P1（既有文档已承认的高风险债务）：未来时间戳污染全设备水位

位置：services/state.py:100-103。

复现：接收一条 timestamp_ms=10^15 的正常数据；设备以新 boot_id 校正时钟后上报 3 条持续异常数据，全部被判为 late，Incident 数为 0。MAX 水位持久化，重启不能自动修复。

设备时间是输入，不应无界支配之后所有检测。需要明确时钟可信策略、允许偏差/隔离、boot/session 时间映射及回放测试模式；不能只按 boot 清空水位而允许旧 boot 重放改变当前状态。该修复需要在在线采集与历史回放之间作清晰取舍。

原始证明：test_bad_clock_does_not_suppress_new_boot_anomalies。当前文档确实声明未做时钟纠偏，但这不消除异常检测失效的风险。

### AUD-003 / P2：持久任务版本有记录，没有执行门禁

位置：services/jobs.py:24-28；services/state.py:187 保存 workflow_version。

复现：把已排队快照标为 unknown-future-workflow，worker 仍按当前实现运行并标记 completed。任务恢复/代码升级时可能静默使用不同语义；这不是外部攻击入口，场景是历史任务兼容或存储损坏。

最小改进是一个明确的支持版本常量和执行前检查；不支持的任务隔离/失败。只有确实需要多个旧工作流时才设计路由或迁移框架。不要先上通用插件系统。

原始证明：test_worker_rejects_unsupported_workflow_version，completed != failed。

## 消融方法与结果

所有实验在进程内替身、临时 SQLite 或内存方法变体中执行。未增加生产绕过开关，未改用户数据库。每一行固定对应场景并比较一个机制；这是确定性机制验证，不是现场误报率、吞吐或模型准确率。

| 场景/机制 | 完整机制 | 移除/替代后 | 可支持的结论 |
|---|---|---|---|
| 事务：事件写入前失败 | 2 条遥测，0 Incident | 3 条遥测，1 Incident | 事务阻止部分提交 |
| 持续窗口：孤立尖峰 | 0 Incident | 1 Incident | 此尖峰被抑制 |
| 持续窗口：持续异常 | 第 3 样本触发 | 第 1 样本触发 | 代价为此用例多等待 2 个样本 |
| 最大采样间隔 | 不成持续异常 | 形成异常 | 稀疏样本不能替代持续性 |
| 请求回执 | 两次请求 1 个 job | 更换请求身份后 2 个 job | 稳定幂等身份能合并重试 |
| 设备范围校验 | 拒绝跨设备参数 | handler 被执行 | 参数范围检查有实际效果 |
| 工具超时 | 慢工具被中止 | 在放宽期限内完成 | 期限约束限制工具等待 |
| 引用 ID 校验 | 伪造引用降级 rules | 伪造引用被接受为 agent | 成员校验防不存在的引用，不证明语义有依据 |
| DB 唯一约束负对照 | 正常重复路径均 1 条 | 正常重复路径仍 1 条 | 普通路径还有事务内预查，不能虚报额外收益 |
| DB 唯一约束旁路写入 | 仍 1 条 | 出现 2 条 | schema 保护旁路写入，保留低成本约束有依据 |
| 冻结遥测快照 | 任务读取 3 条 | 读取后来的第 4 条 | 防提交后上下文漂移；不代表冻结模型/知识库 |
| 待处理容量 | 最多接收 1 个 | 接收 2 个 | 夹具容量边界有效，不代表吞吐能力 |
| 中断任务恢复 | 可重新领取 | 仍 running 无法领取 | 单所有者恢复有效，不代表任意多进程安全 |
| 规则模式手册查询负对照 | 摘要相同，4 次工具调用 | 摘要相同，3 次工具调用 | 此规则路径可尝试简化，未证明模型模式手册无用 |

共有 13 个成对实验函数；唯一约束一组包含普通路径负对照和旁路写入两个观察。原始结果在 audit/ablation-results.json。

## 奥卡姆剃刀与结构审查

- 保留：SQLite 原子事务、唯一约束、单进程有界 worker、只读工具白名单；已有反例支持，成本较低。
- 暂缓：多 Agent、Redis 分布式锁、通用任务工作流框架、自优化路由。当前没有比较证据支持引入。
- 优先简化候选：规则降级路径固定摘要不依赖手册查询；先明确定义最小必需证据，再决定是否跳过查询。
- 高内聚问题：StateStore 同时承担表结构、接入领域决策、Incident 事件、请求回执和任务队列；不是立即拆成多个服务，而是先提炼纯规则结果，维持一个集中事务。
- 重复规则计算：ingest 先 stable_type，detect 又 stable_type；可改为一次纯评估结果由领域层消费。需差分测试，不按文件长度机械重构。
- 低耦合缺口：队列写入与 Runtime 各自写死工作流版本；存储层决定恢复策略，worker 却不校验执行版本。应共享最小契约。
- 知识库、模型和 Prompt 没有完整冻结进任务快照；现有快照只证明遥测/Incident 一致，不能声称重跑能得到相同诊断。
- 容量为待处理任务数，不限制累计数据与日志；同步 SQLite 在 async 路径可能阻塞事件循环。这些是需设计容量/性能实验的债务，本次没有编造负载数据。
